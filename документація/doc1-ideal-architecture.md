# ДОКУМЕНТ 1. Ідеальна архітектура контент-системи (якби будували з нуля)

> Консолідована фінальна версія: базова архітектура + 12 затверджених правок v2 +
> висновки з аналізу 338 повідомлень реальної експлуатації (05–07.2026).
> Це еталон, з яким порівнюється існуюча система в Документі 2.

---

## 1. Сім принципів (порушення будь-якого = клас багів, який ми вже бачили наживо)

1. **БД — єдине джерело правди.** Агент ніколи не відповідає про стан плану з пам'яті
   розмови — тільки live-запитом. (Порушення дало «постів немає» одразу після генерації.)
2. **Дисципліна даних.** Генератори read-only до бази знань; факти (кейси, ціни, цифри)
   не вигадуються — їх або дістали з бази, або їх немає. КБ недоступна → СТОП, а не
   «згенерую з загальних знань».
3. **Атомарність.** Контент зберігається як атоми (hook/body/cta/visual/structure), а не
   блоб — інакше неможливі ні скоринг, ні anti-repeat, ні A/B.
4. **Lazy generation.** Плануємо далеко (скелет), генеруємо близько (J-2). Ніколи 90 днів
   контенту одразу.
5. **Human-in-the-loop.** Публікує людина; медіа генерується тільки після апруву тексту
   (Review Gate). Це і якість, і менший ризик блокувань — усвідомлений вибір, не
   тимчасове обмеження.
6. **Токен-бюджети — числа, не побажання.** Кожен RAG-шар має стелю; сумарний контекст
   юніта ≤ ~2000 токенів.
7. **Анти-цементування.** Жоден висновок «це працює» не існує без confidence /
   sample_size / last_verified; висновки протухають і перевіряються повторно.

## 2. Компоненти системи

```
┌────────────────────────────────────────────────────────────────┐
│ КОНТЕНТ-ПЛАТФОРМА (веб-пульт + БД + API)                        │
│ календар · атоми · аналітика · стратегія · правки · доставка     │
└────────┬───────────────────────────────────────┬────────────────┘
         │ виклик агентів (payload+server_date)   │ SSE/notifications
         ▼                                        │
┌──────────────────────────┐   callback-webhooks  │
│ ОРКЕСТРАТОР АГЕНТІВ       │◄─────────────────────┤
│ A Онбординг  B Контент-   │   ┌──────────────────┴───┐
│ менеджер  C Критик        │   │ МЕДІА-ВОРОНКИ         │
│ D Правки  E Сторіз        │──►│ (зобр/відео/рілс)      │
│ F Аудитор G Продукт-мапер │   │ contract: callback     │
│ H Термінові події         │   │ ready|failed ЗАВЖДИ    │
└─────────┬────────────────┘   └───────────────────────┘
          ▼
┌──────────────────────────┐        ┌───────────────────┐
│ ВЕКТОР-СЕРВІС: 3 індекси  │        │ TELEGRAM           │
│ Global / Static / Dynamic │        │ вхід + доставка +  │
└──────────────────────────┘        │ статуси + апруви    │
                                     └───────────────────┘
```

Telegram і веб — два входи в ту саму воронку Агента B (одна логіка, два тригери).

## 3. Модель даних (ядро)

**Тенант:** Company(project) → users/ролі. Все нижче — з project_id.

**Знання:** Persona (ЦА: болі, мрії, тригери, заперечення, мова), Product (болі що
закриває, трансформація, переваги, priority), LeadMagnet (→продукт, →воронка,
deep-link), **Case {case_id, ніша, проблема, рішення, цифри-результати, дозволені
формулювання}** — кейси тільки як записи з id, ніколи як «пам'ять моделі».

**Стратегія:** SmmStrategy {content_pillars[], intent_distribution{educate .30, sell .20,
trust .20, storytelling .15, entertainment .15}, activeВід, version}, PlatformProfile
(правила кожної мережі: довжина, структури, хуки, частота).

**Контент:** ContentUnit {id, date, platform, format post|carousel|thread|reel|story,
status skeleton|generating|pending_review|approved|media_pending|ready|sent|published|failed,
topic_id, product_id, lead_magnet_id, arc_id, experiment_id, evidence_type case|example|story,
case_id?, atoms{hook_a, hook_b, hook_selected, body, cta, visual_prompt, structure_id},
scores{...}, parent_post_id (для сторіз)}. StoryArc {мета, дати, unit_ids[], статус}.

**Навчання:** Experiment {hypothesis, linked_units, minimum_posts, success_metric,
baseline, status, confidence, sample_size, last_verified}; WinningPattern {тип
hook|structure|topic|pain, платформа, score, confidence, sample_size, last_verified,
status confirmed|needs_retest}; AnalyticsEvent {unit_id, тип реакції, значення, джерело
manual|api}; EditLog {текст, scope local|global, category style|factual|cta|structure|visual,
unit_id?, дата}.

## 4. Пам'ять: три векторні індекси

| Індекс | Зміст | Пише | Читає |
|---|---|---|---|
| **Global Knowledge** (1 на систему) | маркетинг-плейбук, platform_rules, календар свят/інфоприводів | власник системи | всі агенти |
| **Client Static** (на компанію) | бренд/ToV + заборони, персони, продукти, лід-магніти, кейси, short profile (~300-500 ткн) | A, D(global), G | B, C, E |
| **Client Dynamic** (на компанію) | semantic summary постів, використані topic/case_id з датами, edits_log, скоринг, experiments, стан стратегії | B, D(local), E, F | B, C, F, H |

Пошук — тільки скоуплений (папка+метадані-фільтри: platform, score, дата), ніколи
«дай усі правила». Метадані-фільтр — перший рубіж anti-repeat (виключення використаних
topic_id/case_id за 30-60 днів робиться У ЗАПИТІ, LLM-інструкція — другий рубіж).

## 5. Агенти

### A. Онбординг/Стратег
Інтерв'ю (чат/документи/голос) → парсер документів → **дедуплікація і конфлікти**
(анкета vs брендбук суперечать → питання користувачу, не тихе усереднення) →
**Confidence Check** (чекліст повноти: ЦА? кейси? ціни? заборони? — дірки → уточнюючі
питання) → Brand Bible + SMM-стратегія з квотами + short profile → human review →
запис у Static. Вихід: компанія готова до Агента B.

### B. Контент-менеджер (головний, два режими)
**Режим plan:** Intake (server_date + date-resolver: «на 2 тижні» → конкретні дати) →
Task Decomposer (N×формат×платформа×дата — **явне підтвердження користувачу до
генерації**) → Context Loader (бюджети: профіль 300 / продукт+магніт 400 / історія+
anti-repeat 500 / топ-патерни 300 / platform rules 300) → Planning: скелет-сітка з
квотами intent_distribution + story arcs + 80/20 перевірене/експерименти + conflict-check
(2 пости про 1 продукт в 1 день) → збереження скелета (status: skeleton).
**Щоденний cron J-2:** юніти скелета на дату+2 → повна генерація атомів (кожен юніт —
окремий вузький виклик) → Критик → Review Gate.
**Режим single:** «пост про X на завтра» → повний цикл одразу, юніт вбудовується в
існуючий план і в anti-repeat історію.
Callback-фрази («минулого тижня я писав…») — дозволені, коли summary показує зв'язок.

### C. Критик (на кожен юніт, не на план)
Каскад: (1) rule-based без LLM — довжина/CTA/заборонені слова/лід-магніт/мовний фільтр
русизмів; (2) дешева LLM — ToV, стратегія, **case integrity** (evidence_type=case →
факти звірені з карткою case_id; перша особа без історії в базі = reject); (3) вердикт
pass | regenerate(причина) | після 2 ретраїв — ескалація людині. Самооцінки генератора
не існує — перевірка тільки незалежна.

### D. Правки
Класифікація local/global + категорія (style/factual/cta/structure/visual); неясно →
одне уточнення. Local → патч юніта → повторний Критик. Global → diff на підтвердження →
Static + версія стратегії. Pattern-detector: 3+ схожі правки → проактивна пропозиція
зафіксувати правило.

### E. Сторіз-синхронізатор
Підзадача від B для продуктових постів: 3-5 сторіз (тизер→цінність→соц.доказ→нагадування
→CTA в день посту), кожна — атом з parent_post_id і зсувом у часі.

### F. Аудитор (аналітика+навчання, один агент, два режими)
(1) Потік подій: реакція → бали (конфіг: лайк 1, комент 2, перегляд сторіз 1, підписка 5,
продаж 10) → розподіл по атомах юніта → оновлення метаданих Dynamic.
(2) Щомісячний огляд: топ/аутсайдери по платформах → перевірка протухання патернів
(last_verified) → деградація needs_retest → при падінні метрик — пропозиція зміни
стратегії з цифрами → після «так» — нова версія стратегії в статусі testing.

### G. Продукт-мапер
Новий/оновлений продукт → зіставлення з персонами (які болі закриває САМЕ він, щоб 5
продуктів не конкурували одним меседжем) → прив'язка лід-магнітів і воронок → Static.

### H. Термінові події
«Новий кейс / запуск / свято» → класифікація+терміновість → impact (разовий пост чи
міні-серія) → affected units скелета → пропозиція вставити/замінити/посунути (з
обґрунтуванням) → після «так» — патч скелета; контент доженеться сам через J-2 cron.

## 6. Протокол надійності (рівноправна частина архітектури — не «потім»)

1. **Ідемпотентність входу:** processed_messages по message_id (TTL 48 год); повторний
   update — ігнор. Ідемпотентність вебхуків: (unit_id, attempt) один раз.
2. **Debounce 5-8 сек:** серія повідомлень → один склеєний вхід.
3. **Server date injection** у кожен запуск; дата ніколи не живе в контексті сесії.
4. **Session context:** тільки id-посилання, ніяких blob'ів; cap розміру + компакція
   summary замість падіння.
5. **Помилки:** користувачу — людський текст + error_id; стек — власнику окремим каналом.
   Медіа-помилка (кредити/рендер) → чесний failed + причина, не «прийде за кілька хвилин».
6. **СТОП-правило КБ:** база недоступна → зупинка з поясненням, нуль генерації «з голови».
7. **Статуси:** кожен юніт з медіа отримує ready|failed ≤ N хв (watchdog: 1 retry → failed
   + push). Push у Telegram при кожній зміні статусу — користувач ніколи не пінгує.
8. **Робочий бот без маркетингових реактивацій.** Ініціативні повідомлення — тільки
   доставка, статуси, пропозиції F/H.

## 7. Контракти

**Медіа-воронка (вхід):** {unit_id, client_id, platform, format, publish_date,
hook_selected, body, cta, visual{scenario, shots[{desc,duration}], palette, overlays,
music_mood}, linked_story_ids, callback_url}.
**Медіа-воронка (вихід, обов'язково):** POST callback {unit_id, status ready|failed,
result_url|error_code, attempt}. Воронка без callback у продакшен не підключається.
**Telegram-доставка:** щоденний cron: юніти ready на сьогодні → повідомлення (текст+медіа)
→ реакції: ✅ published | правка (→ Агент D з unit_id) | вибір hook_a/hook_b на Review Gate.

## 8. UI платформи
Календар (скелет і готові юніти, арки лінією, drag&drop) · інспектор атомів з балами ·
профіль компанії (Brand Bible, персони, продукти, кейси) · аналітика (ввід реакцій +
дашборд патернів) · експерименти (гіпотези, статуси, вибірки) · історія правок
(local/global, категорії) · версії стратегії з обґрунтуваннями · налаштування доставки.

## 9. Критерії якості системи
Тиждень експлуатації без подвійних відповідей / сирих помилок / мовчань · «на сьогодні»
завжди = фактичне сьогодні · 30 постів без повтору кейса, кейси тільки з case_id ·
жоден медіа-юніт не висить без статусу · падіння КБ = чесний стоп · local-правка міняє
один юніт, global — тільки через diff-підтвердження · токени: ≤2000 контексту на юніт,
Критик +15-30% до вартості юніта, не ×2.
