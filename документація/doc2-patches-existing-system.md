## 0. Межі правок: що НЕ чіпаємо

Лишаються як є: Next.js-платформа і весь UI-каркас · Prisma-модель (тільки розширюємо,
нічого не ламаємо) · мультитенант через projectId · SSE-механіка · банк тем ContentTopic ·
продукти/лід-магніти/deep-link трекінг · медіа-воронки по суті генерації (правимо тільки
їхні виходи) · Telegram як канал доставки/апруву · локальні правки постів за #N (працюють
добре — переносяться без змін).

Єдине, що переписується повністю — **граф воронки «контент менеджер» у flows**. Але це
одна воронка всередині існуючої інфраструктури flows, а не переписування систем.

## 1. Правки інфраструктури flows (Фаза 0 — перший тиждень)

| # | Правка | Що конкретно | Закриває |
|---|---|---|---|
| F0.1 | Ідемпотентність вхідних | Таблиця processed_messages(message_id, ts) у БД flows; перевірка на вході кожної воронки перед виконанням; TTL 48h | [А1] подвійні відповіді |
| F0.2 | Debounce вхідних | Нода-буфер: повідомлення користувача накопичуються 5-8 с, склеюються в один вхід | [Б4] загублені мультичастинні запити |

| F0.7 | Fallback при мовчанні | Якщо воронка не відповіла за N сек — авто-повідомлення «обробляю, зачекай» або «сталася помилка, повтори» | [А2] тиша на 3 запити поспіль |

## 2. Нова воронка «Контент-менеджер v2» у flows (Фаза 1)

Стара воронка (bot 22f2bce5…) архівується як референс. Нова — граф нод:

```
[Trigger TG/Web + F0.1-F0.3]
  → Node "Intent+DateResolver"  (LLM cheap): тип запиту (plan|single|edit|status|question)
       + розбір дат у конкретні; edit → існуюча гілка правок по #N (перенести as-is)
  → Node "TaskDecomposer": N×формат×платформа×дата; ПІДТВЕРДЖЕННЯ користувачу
       («Зрозумів: 4×Threads на 26.06, 1×LinkedIn на 26.06. Ок?») при >3 задач або
       будь-якій неоднозначності
  → Node "ContextLoader": паралельні скоуплені запити у вектор-сервіс з бюджетами
       (профіль 300 / продукт 400 / історія+anti-repeat 500 / патерни 300 / platform 300)
  → [режим plan] Node "SkeletonPlanner": сітка без текстів → save (status=skeleton)
       → відповідь користувачу списком тем/дат; тексти піде генерувати cron J-2
    [режим single] одразу далі
  → Node "UnitGenerator" (цикл по юнітах): атоми hook_a/hook_b, body, cta, visual_prompt;
       evidence_type + case_id обов'язкові в JSON-схемі виходу
  → Node "Critic": rule-based чек (довжина/CTA/стоп-слова/русизми-словник/лід-магніт)
       → LLM-чек (cheap model: ToV, case integrity проти картки кейса)
       → pass | regenerate(причина, max 2) | escalate
  → Node "ReviewGate": текст у Telegram, кнопки ✅ / hook A|B / правка;
       медіа-воронка стартує ТІЛЬКИ після ✅
  → Node "Dispatch": webhook у медіа-воронку за контрактом §4; status=media_pending
```

Плюс окремий **cron-flow "DailyGenerator"**: щодня бере юніти skeleton з датою J+2 →
проганяє UnitGenerator→Critic→ReviewGate. І **cron-flow "DailyDigest"**: юніти ready на
сьогодні → доставка в TG.

Ключові вимоги до нод:
- Кожна відповідь про стан плану («що на сьогодні», «чи є пости») — тільки через
  list_posts до content2, ніколи з контексту [Б3].
- JSON-Schema на стиках нод; невалідний об'єкт → повернення, не «інтерпретація».
- Генераторні ноди read-only до знань; помилка вектор-сервісу → СТОП-повідомлення
  користувачу [Г1], без генерації з загальних знань.

## 3. Правки content2 (БД + API)

### 3.1. Prisma-міграції (адитивні, нічого не ламають)
> **РІШЕННЯ (узгоджено 2026-07-18, Варіант A, задача Ф3.0/#323):** strategic-атоми — на
> рівні ЮНІТА (`PostGroup`), а не слайда (`PostItem`). Скоринг теж на рівні юніта. Причина:
> для каруселі/треду hook/cta розподілені по слайдах, тож на PostItem вони не лягають.
- **PostGroup (ЮНІТ)** + strategic-атоми: `hook_a, hook_b, hook_selected, cta, structure_id,
  evidence_type enum(case,example,story), case_id?, scores Json` (скоринг юніта, #248)
  + `arc_id?, experiment_id?, skeleton bool` (двофазність, арки).
- **PostItem** — render-шар: `content` (слайд/повідомлення) + `visual_prompt` + `slide_title`
  (+ опц. per-item visual score). Body: single = 1 item; carousel/thread = набір `content` item'ів.
- **Stories** — НЕ N item одного посту, а N окремих юнітів (`PostGroup`) у звʼязці `arc`
  з `parent_post_id` і зсувом у часі (Агент E).
- Нові моделі: **Case** {projectId, title, niche, problem, solution, metrics Json,
  allowed_claims}, **StoryArc**, **Experiment** {hypothesis, minPosts, metric, baseline,
  status, confidence, sampleSize, lastVerified}, **WinningPattern** {kind, platform,
  score, confidence, sampleSize, lastVerified, status}, **EditLog** {scope, category,
  unitId?, text}, **ProcessedWebhook** {unitId, attempt} (ідемпотентність F2.4).
- **KnowledgeEntry** → міграція в вектор-сервіс (див. §5), модель лишається як legacy-read.

### 3.2. API
- `POST /api/webhooks/generation-event` — розширити: приймає `status: ready|failed` +
  `error_code` + `attempt`; ідемпотентність по (unitId, attempt); при failed —
  Notification + **push у Telegram-чат проєкту** (нове: зараз тільки SSE у веб) [Г1].
- `generation-watchdog` — доробити дію: завислий юніт → 1 авто-retry → failed + TG-push
  + алерт власнику. Зачистка накопичених generating_text/failed без тексту.
- `/api/agent-tools` + нові дії: `save_skeleton, get_skeleton_due(J+2), get_cases,
  check_repeats(topic_ids, case_ids, days), log_edit, get_patterns(platform),
  save_experiment, score_event`. І скоупи/rate-limit на токен (аудит §15a-7).
- `POST /api/analytics/manual` — форма вводу реакцій → AnalyticsEvent → перерахунок
  scores атомів (ваги — конфіг проєкту).

### 3.3. UI (мінімум для циклу)
Картка поста: тема/категорія/кейс/evidence_type видимі (#244) · календар: skeleton-юніти
відображаються «плейсхолдером» до генерації · сторінка «Кейси» (CRUD) · сторінка
«Експерименти» · форма вводу аналітики + дашборд топ-хуків/тем по платформах ·
ротація палітр у налаштуваннях генерації зображень [В4].

## 4. Правки медіа-воронок flows (Фаза 2)

Аудит УСІХ: content-stories-generator, content-carousel, content-ai-bg-pro, обидві
avatar-*, video-basic-subs, video-remotion, resizer, hyperframes. Для кожної:
1. На фінальній ноді — POST generation-event {unitId, status:ready, result_url, attempt}.
2. На КОЖНІЙ гілці помилки (включно з таймаутом провайдера і insufficient credit) —
   POST {status:failed, error_code}. Заборонено «мовчазний» вихід.
3. Вхід — за контрактом §7 Документа 1 (уніфікований JSON; узгодити з наявними полями).
Правило підключення: воронка без обох callback'ів у продакшен-список не потрапляє.

## 5. Вектор-мікросервіс (#263) — критичний шлях Фази 1

Три колекції: global / static:{projectId} / dynamic:{projectId}; пошук з
metadata-фільтрами (platform, score, дата, topic_id, case_id) — ваша нода «Векторна
база» це вже вміє після доробки метаданих (ви підтвердили).
Міграція: KnowledgeEntry → чанки в static; ContentTopic/використані кейси → dynamic;
плейбук/platform_rules → global. get_rules у боті замінюється на скоуплені запити.

## 7. Ризики шляху правок і як їх гасимо

1. **Стара і нова воронка контент-менеджера в перехідний період.** Гасимо: жорсткий
   cutover — нова воронка на тому ж боті, стара архівується одразу; жодного тижня
   «двох ботів».
2. **Міграція KnowledgeEntry у вектор може загубити правила.** Гасимо: legacy-read
   лишається; тиждень паралельної роботи з логом «що знайшов вектор vs що знайшов би
   get_rules».
3. **Callback-аудит медіа-воронок виявить більше дірок, ніж очікуємо** (судячи з логів —
   виявить). Гасимо: правило продакшен-списку (§4.3) + watchdog як страховка.
4. **Спокуса почати з Ф1 (цікаве), а не Ф0 (нудне).** Не можна: весь червень баги агента
   було неможливо відрізнити від багів транспорту. Ф0 — перша.
