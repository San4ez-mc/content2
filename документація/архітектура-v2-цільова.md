# Цільова архітектура контент-системи FINEKO (v2)

> Для затвердження перед Ф1 (перенесення контент-менеджера на content2).
> Легенда: ✅ є · 🟡 частково · ❌ будувати.

---

## 0. Компоненти — де що живе

| Компонент | Що це | Роль |
|---|---|---|
| **content2** (`content2.fineko.space`, Next.js + Postgres) | Веб-пульт + БД + API | **Єдине джерело правди** для структурованих даних і контенту |
| **flows** (`flows.fineko.space`) | Двигун воронок + AI-агенти (Claude/Gemini) | Оркестратор: діалоги, генерація, виклики |
| **Вектор-сервіс** (`:4500`) | 3 семантичні індекси (Vertex ембединги) | Пам'ять для RAG і anti-repeat |
| **Telegram** (`@fineko_content_bot`) | Вхід + доставка | Канал спілкування з користувачем |
| **Медіа-воронки** (image/video/remotion, Fal/Vertex/HeyGen) | Генерація візуалу | Створення зображень/відео за контрактом |

Ключовий принцип: **вся AI-логіка — у flows-воронках (нодах); усі дані — у content2; семантика — у векторі.** content.fineko.space (стара PHP-система) — **виводиться з обігу**.

## 1. Дані: звідки що береться, куди йде

| Шар | Сховище | Хто ПИШЕ | Хто ЧИТАЄ |
|---|---|---|---|
| Продукти, Персони, Кейси(з case_id), Лід-магніти, SMM-стратегія, Банк тем | content2 БД (моделі) | Онбординг (A), Продукт-мапер (G) | Контент-менеджер (B), Критик (C) |
| Бренд/ToV, заборонені слова | content2 `KnowledgeEntry(brand)` | A, D | B, C |
| Сирі онбординг-документи | content2 `KnowledgeEntry(onboarding-doc)` | A (readFile) | парсер |
| **Контент** (юніти, атоми hook/body/cta, статуси) | content2 `PostGroup/PostItem` → v2 `ContentUnit` | B, D | B, доставка, аналітика |
| Медіа-файли | content2 `MediaItem` (+ диск) | медіа-воронки | доставка |
| **Семантика** (для пошуку/anti-repeat) | вектор: 3 індекси | A/B/D/F | B/C/E/F |

## 2. Три векторні індекси (пам'ять)

| Індекс | Зміст | Пише | Читає |
|---|---|---|---|
| **Global** (1 на систему, projectId=null) | маркетинг-плейбук, правила платформ, календар свят/інфоприводів | власник | усі агенти |
| **Client Static** (на компанію) ✅ | бренд/ToV+заборони, персони, продукти, лід-магніти, **кейси**, short profile | A, D(global), G | B, C, E |
| **Client Dynamic** (на компанію) ❌ | semantic summary постів, **використані topic_id/case_id з датами**, edits_log, скоринг, стан стратегії | B, D(local), E, F | B, C, F |

**Anti-repeat** = метадані-фільтр у ЗАПИТІ (виключити використані topic_id/case_id за 30-60 дн) + LLM-інструкція. Перший рубіж — Dynamic-індекс.

## 3. Онбординг (Агент A) — ✅ вже працює

```
Telegram (/start onboard)
  → flows: воронка onboard
     1) httpRequest → content2 /api/webhooks/onboarding-profile  → {known, gaps}  (що вже відомо)
     2) Продукти (Claude, список) → save products[]
     3) Матеріали: readFile-нода читає PDF/DOCX/TXT → save doc
        → /api/webhooks/onboarding-extract → flows /api/rag/generate (Gemini)
           → витягує продукти/персони/КЕЙСИ (кейс→productId) → content2 БД
     4) Персона+ToV, Стратегія+~50 тем, Лід-магніт (Claude) → save
     5) кожен save → syncStaticToVector → вектор Client Static
```
**Результат:** content2 БД + вектор Static заповнені. Готово до Агента B.

## 4. Гейт `/start` (маршрутизація) — ❌ будувати (швидко)

```
Telegram (/start, без слага)
  → flows platformBotHandler → resolveTargetBot
     → нода-гейт: httpRequest content2 /api/webhooks/onboarding-profile → gaps?

        • ПОВНО → воронка content-manager

Поріг готовності: **продукти + ≥1 персона + ToV + стратегія**. Захист від циклу: після онбордингу → назад у контент-менеджер.

## 5. Контент-менеджер (Агент B) — ❌ Ф1, ГОЛОВНИЙ БЛОК

Лишається воронкою flows, але **читає/пише content2 + вектор** (замість content.fineko.space). Уся захардкоджена стратегія з `CONTENT_CORE_RULES` → переїжджає у структуровані дані content2 (стратегія, теми, platform-профілі, правила) + Global-індекс.

### Режим ПЛАН (запит «зроби план на 2 тижні»)
```
1. Intake       — запит + СЕРВЕРНА дата → date-resolver («2 тижні» → конкретні дати)
2. Task Decomposer — N × формат × платформа × дата → ПІДТВЕРДЖЕННЯ користувачу до генерації
3. Context Loader — RAG з бюджетами токенів:
      content2: продукти/персони/стратегія/банк тем (live-запит)
      вектор Static: бренд/ToV, кейси
      вектор Dynamic: anti-repeat (використані теми/кейси за 30-60 дн)
      вектор Global: правила платформ, інфоприводи
4. Planning     — скелет-сітка (дата×платформа×формат) з квотами intent_distribution
                  + story arcs + 80/20 перевірене/експерименти + conflict-check
                  → content2 ContentUnit (status=skeleton)
```
### Щоденний крон J-2 (генерація близько)
```
5. Юніти на «сьогодні+2» → повна генерація АТОМІВ (hook/body/cta/visual_prompt)
   — кожен юніт окремим вузьким Claude-викликом (≤2000 ткн контексту)
6. Критик (Агент C) → pass | regenerate(причина) | ескалація
7. Review Gate → текст у Telegram; медіа стартує ТІЛЬКИ після ✅ апруву
8. Медіа-воронка (контракт: callback ready|failed ЗАВЖДИ) → content2 MediaItem
9. Dispatch → щоденна доставка ready-юнітів у Telegram + статуси
```
### Режим SINGLE («пост про X на завтра»)
Весь цикл одразу; юніт вбудовується в план і в anti-repeat історію.

## 6. Агенти-супутники

| Агент | Що робить | Читає / Пише |
|---|---|---|
| **C. Критик** ❌ | На КОЖЕН юніт: rule-based (довжина/CTA/русизми/заборонені) → LLM (ToV, стратегія, **case-integrity: факти звірені з case_id**) → вердикт | Static (кейси) / — |
| **D. Правки** 🟡 | local (патч юніта→ре-критик) / global (diff-підтвердження→Static+версія стратегії); 3+ схожі → пропозиція правила | content2, Static/Dynamic |
| **E. Сторіз** ❌ | 3-5 сторіз на продуктовий пост (тизер→цінність→доказ→CTA) | Static / content2 |
| **F. Аудитор** ❌ | скоринг реакцій → Dynamic; місячний огляд → пропозиція зміни стратегії | AnalyticsEvent / Dynamic |
| **G. Продукт-мапер** ❌ | новий продукт → зіставити з персонами → лід-магніти | content2 / Static |
| **H. Термінові події** ❌ | нова подія/свято → патч скелета | content2 |

## 7. Протокол надійності (частина архітектури, не «потім»)

- ✅ **Ідемпотентність входу** (processed_messages, TTL 48г) — Ф0.1
- ✅ **Debounce 5-8с** + серіалізація сесії (кілька повідомлень → один вхід)
- ❌ **Server date injection** у кожен запуск (дата не з контексту сесії)
- 🟡 **Context = тільки id-посилання** + cap + компакція (не blob'и)
- 🟡 **Помилки:** людський текст + error_id користувачу; сирий стек — власнику
- 🟡 **СТОП-правило КБ:** вектор недоступний → чесний стоп, нуль генерації «з голови» (є в `/vector/search`)
- ❌ **Статуси:** кожен медіа-юніт ready|failed ≤ N хв (watchdog: 1 retry→failed+push) — Ф2
- 🟡 **Робочий бот без маркетингових реактивацій** (Ф0.5)

## 8. Що вже є / що будувати

**✅ Зроблено:** content2 (моделі + сторінки), онбординг (product-first, парсер документів, readFile-нода), вектор Client Static + пошук, надійність (ідемпотентність, debounce, лок, вотчдог), Vertex-міграція.

**❌ Будувати (порядок):**
1. **Гейт /start** (швидко) — маршрутизація по повноті профілю.
2. **Ф1 — Контент-менеджер на content2:** пайплайн нод (Intake→Decomposer→Context Loader→Planning→J-2→Критик→Review Gate→Dispatch); винести `CONTENT_CORE_RULES` у структуровані дані + Global; Client Dynamic наповнення (anti-repeat); Критик (C).
3. **Ф2 — Статуси генерацій:** контракт callback усіх медіа-воронок, push, watchdog.
4. **Ф3 — Навчання:** атоми+скоринг, Аудитор (F), Продукт-мапер (G), Термінові події (H).

**Міграція:** контент-менеджер `content-manager-v2` перемикається з `content.fineko.space` (проєкт 2) на content2; стара PHP-система виводиться.

## 9. Один погляд — повний потік

```
ОНБОРДИНГ:  людина → onboard(flows) → content2 БД + вектор Static ✅

/START:     людина → гейт(перевір content2) → онбординг АБО контент-менеджер

КОНТЕНТ:    запит → Intake(дата) → Decomposer(підтвердження) →
            Context Loader(content2 + вектор Static/Dynamic/Global) →
            Planning(скелет→content2) → J-2(атоми) → Критик → Review Gate(Telegram) →
            медіа-воронки(callback) → content2 MediaItem → Dispatch(Telegram) →
            реакції → Аудитор → Dynamic(навчання) ↺
```
```

Все обертається навколо **content2 як джерела правди** і **вектора як пам'яті**; flows — оркестратор, Telegram — вхід/вихід.
